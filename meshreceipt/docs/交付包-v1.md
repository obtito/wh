# 离线交付包 v2（兼容 v1）

更新：2026-10-07。本文说明已实现的离线导出与独立消费，不代表公开托管、真实 AI 或 BOT 主网已经完成。

## 使用流程

1. 重新启动本地后端后，在验收实验室用自有样例创建一个新任务。旧任务没有冻结的来源授权，仍可下载原始结果，但不允许导出交付包。
2. 完成处理后，确认愿意一并导出原模型和处理结果。PASS 可以选择“导出合格交付包”；所有可验证的完成尝试可以选择“导出履约取证包”。
3. 将下载的 JSON 文件交给另一位使用者；另经可信渠道确认签名者地址、应用实例和服务标识。包内提供身份信息本身不是信任依据。
4. 从可信渠道另取支持 v2 的本轮工具源码与 `package-lock.json`，在工具目录运行 `npm ci --ignore-scripts` 安装锁定依赖，使用页面“独立复核与提取”给出的命令。新包内 `README.txt` 同时提供环境、命令、工具版本、退出码、打开模型与许可/质量边界说明。安装依赖需要网络；安装后的消费命令只读交付包，不访问发布者数据库、私钥或后端，也不请求网络。包本身不含工具源码和依赖。

```sh
npm run consume -- /absolute/path/to/bundle.json --issuer TRUSTED_ADDRESS --instance TRUSTED_INSTANCE_UUID --provider TRUSTED_PROVIDER_ID --out /absolute/path/to/new-directory
```

以上大写值需替换，输出目录必须不存在。省略 `--out` 时只验证，不提取。确认工具来源后再运行；不要执行陌生交付包里的任意脚本。

成功提取后，用支持 GLB 的查看器打开 `model.glb`。`verification.json` 给出本机复核结果，`report.json` 包含具体规则与检查项。新增 `seal.json` 原样保留发布签名，与 `manifest.json` 和全部固定材料一同保存；不要只转交模型或无签名的本机复核结果。只剩提取目录时，可按清单文件重建原 JSON 封装再用可信工具复核，测试已覆盖此流程；当前 CLI 仍接收 JSON 包，不直接接收目录。工具库能重新读取模型不代表所有渲染器都兼容；视觉效果与真实业务使用还需相应验证。

## 格式与信任边界

JSON 顶层固定为 `schema`、`manifest`、`seal`、`files`。新导出使用 `meshreceipt.bundle.v2` / `meshreceipt.release.v2`，消费端也接受严格的 v1 五文件包；旧消费工具不保证读取 v2，请更新可信工具。两种版本各使用对应签名域，不能替换版本标签复用签名。版本升级只改封装和说明，不改冻结规则、报告算法或旧包字节。采用 Base64 内嵌文件，便于离线传递；这会增加封装体积，不是压缩算法。为保留既有文档链接，本文路径仍沿用 `交付包-v1.md`。

v2 仅允许以下六个固定名称；v1 不含 `README.txt`，消费时不会伪造一份说明加入旧签名清单：

| 文件 | 内容 |
| --- | --- |
| original.glb | 获授权的原模型 |
| model.glb | 确切版本的处理结果 |
| policy.json | 冻结验收规则 |
| report.json | 逐项检查、工具版本与报告指纹 |
| delivery.json | 服务交付签名与原始载荷 |
| README.txt | 安装/复核/打开方法、工具版本、退出码及边界说明；同样绑定文件指纹与清单签名 |

发布清单绑定任务、尝试、来源声明和每个文件的大小/SHA-256，其规范化哈希作为本次发布标识。清单另加域分离的 EIP-191 签名，避免模型以外的元数据被修改后仍误认为原发布。

演示中同一团队控制的服务身份同时签署交付和发布清单。这不是独立验证，也不是创作者版权证明。`project-owned-sample` / CC0 仅为发布者对本项目自有样例的授权声明，不给第三方地标授予许可；未加入主网凭据。

消费者必须显式提供可信的 issuer、instance、provider。先校验发布签名、文件白名单与指纹，再检查任务绑定和交付签名，最后运行本机可信验收器，要求报告哈希一致。工具/依赖版本不同可能导致复算不一致，应检查版本，不能忽略失败。

合格包必须重新计算得到 PASS。有效签名的 FAIL 取证包可以被核验，但不会成为合格资产；PASS 也可以导出为取证用途，仍不被工具自动标成合格发布。

## 接口与退出码

接口：`POST /api/tasks/:taskId/attempts/:attemptId/bundle`，沿用本机来源、JSON 类型与 `x-meshreceipt: local-demo` 检查。

```json
{"kind":"qualified","confirmDistribution":true}
```

取证使用 `kind: "evidence"`。导出时重新复核确切文件快照，文件遭替换、报告/签名不一致、授权缺失、任务未完成都会拒绝。旧的模型/报告 GET 接口继续用于诊断，不因 FAIL 被整体禁用。API 同时最多执行一个包导出复核，忙时需稍后重试。

| CLI 退出码 | 含义 |
| --- | --- |
| 0 | 合格包完整性、身份签名与独立复算通过，规则结果 PASS |
| 1 | 取证包验证成功，实际规则结果 FAIL；不是工具运行错误 |
| 2 | 取证包验证成功，但不是合格发布，例如 PASS 取证包或 INCONCLUSIVE |
| 3 | 包校验、签名/信任配置、复算或文件操作失败 |

包上限 32 MiB，单个 GLB 沿用 10 MiB 支持范围，单个 JSON 材料上限 512 KiB，说明文件上限 16 KiB。拒绝未知文件名、路径穿越、符号链接、FIFO/目录等非普通输入文件、非规范 Base64 和大小不符。读取前检查类型，再以非阻塞/no-follow 标志打开并复核类型、大小及文件身份；当前 macOS 上的“普通文件检查后换成 FIFO”反例也被及时拒绝。这些平台标志在不支持的平台不提供同等竞态保证。验证失败不创建提取目录；已有目录不覆盖。如果验证后磁盘写入失败，可能留下部分新目录，需要检查错误后手动处理，不视为提取成功。

消费工具没有强恶意文件隔离，不应处理未经确认身份的任意来源；这些边界检查不等于通用解析器沙箱。当前规则没有覆盖材质/纹理的完整视觉正确性。
